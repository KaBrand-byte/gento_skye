## 双臂空载动作程序

已按[实施方案](方案.md)实现 Python 顺序流程：准备位→ 接盘位→ 触发任务 → 同步前伸 100 mm → 同步下降 100 mm → 两侧各退出 100 mm → 返回准备位。夹爪控制、人工交接、导航和夹持／放置检测均显式跳过。程序只记录空载运动是否完成，不代表实际递盘或放盘成功。

使用 Python 3.10 或以上版本。程序本身只依赖标准库；真机运行使用外部 SDK 0407 的 `PYTHON_SDK/GentoRobot.py` 和同目录原生库，不复制 SDK 到本项目。默认 SDK 路径为 `/home/gento/robot_sdk/tianji-robot-SDK`，可用 `GENTO_SDK_ROOT` 环境变量或 JSON 中的 `sdk_root` 修改，环境变量优先。

在项目根目录执行离线配置检查，不加载 SDK，也不连接设备：

```bash
python3 -m skye_task check --config config/default.json
```

在设备当前姿态下，只读取反馈和模型、计算完整后续路径：

```bash
python3 -m skye_task plan-check --config config/default.json
```

`plan-check` 从**当前关节反馈**开始检查前伸、下降、退出及双臂回准备位，适合停在接盘位后诊断；要求升降已处于接盘高度 450 mm，腰、头符合固定姿态。它不将机器人移动到配置点位，也不执行或验证升降调整。此命令不切换模式、不发送保持位置或轨迹指令，失败时也不发送停止指令。结果独立写入 `runs/plan-check.json`，保留失败段的起始／目标矩阵、参考关节和位移。规划通过仍需真机验证实际路径。

真机空载运行：

```bash
python3 -m skye_task run --config config/default.json --result runs/latest.json
```

`run` 会立即连接 `6.6.7.190`、进入位置模式并运动到准备位和接盘位。每个点位先执行双臂 MoveJ，再单独调整升降并等待稳定；接盘高度到位后，按一次 Enter 触发余下动作，之后没有人工继续节点。等待触发时仍检查双臂与固定部件反馈。Ctrl-C / SIGTERM 请求停止双臂轨迹；若升降正在调整，则同时请求保持其当前反馈位置。`Sequence.request_stop()` 是程序调用入口。

连接、规划、上传、启动、执行或超时失败均终止推进并请求停止双臂，无自动重试、自动松爪、自动下使能或自动收臂。正常完成后保持准备位的位置控制；退出时释放 SDK 连接和运动学资源。

## 配置与执行约定

[默认配置](config/default.json)支持部分覆盖，完整默认值可用 `check` 查看。点位、固定部件反馈、速度、加速度、各段采样频率、到位容差、稳定时间和超时均可配置。稳定时间默认 1 s，预留的夹爪／交接等待均为 1 s，当前流程不使用这些等待。

| 项目 | 约定 |
| --- | --- |
| SDK／控制器 | 版本前缀必须为 `000407` |
| 关节和姿态角 | °；MoveJ 规划比例为 `(0, 1]`，默认速度／加速度均 0.1 |
| 直线运动 | mm、mm/s、mm/s²；默认速度／加速度均 100 |
| 运行比例 | 两臂设为 100%，由规划参数决定速度；模式切换比例默认 10% |
| 腰、头与升降 | 腰部 2 轴、头部 2 轴；升降 1 轴；SDK 数组多余槽位仅补零 |
| 参考方向 | 机器人参考系 +X 前方、+Y 左侧、+Z 上方；使用 SDK 躯干正运动学和各肩部旋转矩阵转换位移 |
| TCP | 从控制器 `tool_kine` 读取并应用到运动学／规划；各直线段保持起始姿态，执行中监测 TCP 配置变化 |
| 轨迹时基 | 默认 50 Hz，沿用厂商示例；所有规划频率必须与 `controller_trajectory_hz` 相等 |

SDK 的轨迹上传接口只有关节点，没有采样频率字段，也没有可用的执行频率查询接口。**真机首跑前需核对控制器实际轨迹执行频率**，并将 `controller_trajectory_hz` 和各段 `frequency_hz` 同时改为该值；代码的配置一致性检查不能验证控制器实际时基。

双臂示教关节值及 `ready_lift`／`receive_lift` 均显式写入默认 JSON。程序按有效轴数检查腰、头已在零位容差内，并保持连接时的位置。初始化接受 450–500 mm 范围内的升降反馈（含配置容差），以支持从任一点位重新运行。各次双臂运动期间升降保持固定；先收臂到准备姿态，再调整至 500 mm；接着双臂到接盘姿态，再降至 450 mm。前伸、下降和退出均在 450 mm 执行，末尾先收臂再升至 500 mm。

升降使用位置指令和配置中的模式速度／加速度比例（默认 10%），与双臂轨迹分步执行。程序检查升降实际位置和由新反馈帧估算的速度，持续稳定 1 s 后继续；调整期间检查双臂静止、腰头不变，超时或停止时请求保持升降当前反馈位置。模式异常、自由度不匹配、固定姿态偏离或反馈停更时结束流程。SDK 返回的规划路径尚不代表真机路径已验证。

每段运动均先完成双臂规划与上传，再用同一双臂掩码启动；返回掩码必须包含两臂。直线规划按当前关节选择邻近逆解，不额外固定肘平面；上传前检查轨迹首点与实际起点连续。完成判定同时检查启动进展、轨迹空闲、实际关节／直线目标位姿、低速和持续稳定，避免将启动前的 `traj_state=0` 当成完成。已经到位的静止臂仍参与双臂启动，上传 5 个相同的当前位置点。SDK 0407 要求整条轨迹有 5–5000 个点；原生规划不足 5 点时保留原路径，在末尾重复终点补足，执行时长按补齐后的点数计算。

结果写入 `runs/latest.json`（可用 `--result` 修改），包含各段执行记录、升降目标／实际到位位置、错误与停止失败信息、版本／自由度／TCP／初始固定反馈，以及 `motion_completed`、`grasped`、`placed`。夹爪动作记录为 `not_executed`，夹持／放置判定为 `skipped`，实际结果为 `null`。

后续夹爪统一入口与导航调用／到站停稳反馈协议见 [interfaces.py](skye_task/interfaces.py)。夹爪入口当前抛出 `NotImplementedError`，没有开合模拟或成功返回；空载流程不调用这些预留接口。

## 离线验证

```bash
python3 -m unittest discover -s tests -v
```

测试用替身仅用于验证运动编排和 SDK 调用契约，不提供生产模拟模式。60 项测试通过，覆盖连续运行两轮、静止臂最小点数、短轨迹补齐、动作顺序、坐标转换、固定有效轴、升降 500→450→500 mm、升降卡住／取消／双臂漂移时的停止、启动前空闲、实际到位、稳定时间、反馈停更、版本不匹配、上传失败、部分启动、超时、首点连续性、失败输入记录和只读规划不下发控制指令。

用户首次真机实验使用旧点位，前伸 150 mm 在规划阶段失败，见[首次实验记录](docs/experiments/2026-11-11-first-run.md)。更正点位及 100 mm 前伸／下降后，先通过[离线规划验证](docs/experiments/2026-11-11-corrected-poses.md)，随后用户于 14:35–14:36 完成整轮真机空载流程。紧接着重新启动，在已处于准备位的分支上传了仅 2 点的保持轨迹，SDK 返回 `-19`；现已修正为符合 SDK 最小点数要求。详见[完整运行及重复启动修复记录](docs/experiments/2026-11-11-repeat-run.md)。重复启动修复已通过离线回归测试，尚待用户再次真机运行。
